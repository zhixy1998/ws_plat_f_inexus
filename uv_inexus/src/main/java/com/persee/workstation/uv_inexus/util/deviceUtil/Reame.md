拆分仪器模块总体思路

1，DevOperationUtils  作为与业务层交互的接口，提供各类仪器操作方法，例如查找仪器、连接仪器、初始化、校零等等

各功能有需要的参数作为方法传参，由业务层提供，该接口提供业务层需要的处理后的结果，由于各类参数差别较大，仪器端无法确认业务需要哪些结果，
故结果参数可放在统一的实体类中，仪器端将可以处理的后所有能得到的结果全部存入结果实体类，并返回，由业务层去选择用哪些参数

2，OperationConstants 常量类，用于仪器模块的常量传参

3，UdpReceiveThread  接收线程，仅负责接收报文并推送到接收队列里，暂定在仪器连接成功之后开启，断开连接后关闭。
    接收线程需要区分，端口，网口，以及wifi接收方式，存放数据位置一致
    问题：后续出于多线程问题考虑，建议接收队列采用map或者其他结构，根据报文带的ip来作为key值区分
        串口端，可用不用串口号来做区分，处于串口接收问题，可能不同串口需要不同的接收线程，但存放到队列的方式仍以串口作为Key值

4，UdpSendUtil  发送线程，用于报文发送，接收解析和处理，UdpSendUtil（后续简称send）与DevOperationUtils（后续简称dev）相比：
    
    dev负责解析业务层参数，并将其转换为发送报文，随后调用send并接收返回，根据返回值，判断指令执行结果---失败报错返回，成功解析转化为返回参数
    send主要负责，发送报文，随后从队列中获取所需的返回报文，接收成功--调用解析工具类进行报文解析并返回，接收失败--重发或超时后返回报错

5，UdpResponseDeal 负责报文解析，根据不同仪器解析方式不同，需要区分，通用指令和仪器指令，后续解析出结果并返回
    解析报文，根据仪器来做区分，不同型号仪器，返回的报文可能不同，解析格式也不同

6，OperationResultEntity  返回业务层的结果参数实体类，暂定所有属性均放到给实体类中，后续根据需要看是否需要拆分。

7，考虑仪器管理问题，业务层传序列号，接口方法里去转换ip或串口，后续和处理端需要根据ip或端口来取报文处理。
    同时，该设计应该支持多线程，多仪器同时连接功能，若后续有问题再调整---注意，多仪器连接，仅支持同种连接方式，网口或串口或wifi

8，在切换仪器时，需要断开当前仪器才可。

总结，该方式，将报文发送，报文接收，报文解析相互拆开，同时与业务层拆分开，避免了业务层直接参与仪器指令调用。

具体开发注意事项：

    1.由于仪器为单线程，所以发送指令前，需要抢占仪器，避免多指令发送，造成报文出错。同时需要维护仪器状态，目前有实时回显线程在维护，后续可尝试由接收或发送线程来维护
    2.由于仪器连接后，其他pc不可连接，所以在切换仪器时，需要断开当前仪器，该功能需要业务层维护和仪器端同时维护，暂时可断开位置包括：
        手动断开、退出登录、查找仪器时应断开所有仪器连接
    3.  针对断电重启即非正常退出等异常情况，程序启动时，需要执行检测工作。
        根据数据库连接的仪器，尝试与仪器重新构建连接，连接成功可继续使用，连接失败的需断开，连接成功后更新仪器当前信息
        检测过程中，仪器ip可能会发生变化，所以，通过ip连接后，需要确认序列号，后续根据序列号来更新数据库信息。
            处理时，取出所有序列号和ip，随后测试连接，根据当前ip实际对应的序列号，取数据库中的数据，然后根据当前仪器的信息来更新数据库。
